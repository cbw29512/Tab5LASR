# LASR microSD storage implementation — first guarded milestone

Date: 2026-11-18

## Definition of Done (software slice)

- A portable C journal writer makes a unique session folder on an already-mounted microSD volume; records ordered, monotonic-time shot events; emits `shots.csv`, `session.json` and `target.json`; verifies file size and CSV record count before claiming SAVED.
- A failed/incomplete session retains `shots.pending` for later recovery; corrupt IDs are rejected; no existing session directory may be reused or overwritten.
- A separate USB storage-ownership state machine refuses USB export until recording is idle, writes are flushed and Tab5 has unmounted the filesystem; resumption requires confirmed USB host eject before local remount.
- Host-side tests compile with `-Wall -Wextra -Werror -fsanitize=undefined`; CI runs them. **Passing tests never establishes on-device functionality.**

## Data schema

`lasr_session_store_t { state, folder, session_id, target_id, calibration_revision, delay_ms, shots, last_elapsed_ms, total_score, journal, last_errno }`.

`lasr_shot_t { sequence, elapsed_ms, split_ms, score, x_norm, y_norm, zone }`. Elapsed and split times must be generated by the monotonic shot-clock engine after GO, not by the writer.

`lasr_transfer_guard_t { state, writer_idle, files_flushed, local_unmounted, usb_host_released }`. Guard states: LOCAL → PREPARE_USB → USB → EJECTING → LOCAL.

## Implementation now in review branch

- `onboard/main/lasr_session_store.{h,c}`: session state, append, finish, error handling.
- `onboard/main/lasr_session_fs.{h,c}`: bounded path creation, fsync/close, readback, atomic-ish temporary metadata replacement. FAT rename is **not power-fail atomic**; keep the pending journal.
- `onboard/main/lasr_transfer_guard.{h,c}`: exclusive SD owner gate; no USB MSC controller or network service is started by this module.
- `onboard/tests/test_lasr_session_store.c` and `test_lasr_transfer_guard.c`: cross-platform host tests.
- `.github/workflows/lasr-session-storage-tests.yml`: host CI tests.

## Integration ordering — no camera regression

1. Confirm current pinned BSP `espressif/m5stack_tab5==1.3.3` exposes SD mount and unmount; verified against the official v1.3.3 API. Board's filesystem root comes from `BSP_SD_MOUNT_POINT`.
2. **Before device mount**, audit the BSP's exact `format_if_mount_failed` behavior. Never auto-format media on mount failures; if the default BSP mount can format, use explicit SDMMC configuration with that flag disabled.
3. Start a dedicated SD owner task only after existing display/I2C, P4 power-latch and battery recovery controls are initialized. The current `onboard_camera_run()` function blocks while streaming; SD owner must not be put after it in `app_main()` or run synchronously in the frame loop.
4. Route camera laser event outputs through a bounded queue, timestamped **before** enqueue. The SD task consumes them and calls `lasr_store_append`. Writer's immediate `fflush` is **not** latency-tested on the physical device; tune flush/fsync cadence based on measured performance. A slow or failed card must not stall camera capture.
5. Explicitly show storage `UNSAVED` until final writer succeeds, and preserve in-memory shots on errors. Journal replay/recovery UI is **not yet implemented**.
6. Add USB-C TinyUSB MSC backend only after hardware USB port enumeration and clear exclusive ownership; never allow Windows and Tab5 to mount/write the same FAT volume simultaneously.
7. Add Wi-Fi download only after C6/ESP-Hosted compatibility and existing 1 MiB app partition limit are resolved. No partition changes, forced flash or automatic C6 flashing.

## Known incompleteness

- This is **working source code plus host tests**, but not wired to live Tab5 SD mount, device touch controls, camera laser detection, microSD ownership task, USB MSC driver, or Wi-Fi download handler.
- A strong crash recovery UI, real microSD `fsync` durability, card removal and saturation handling, USB eject/hot-unplug behavior, and power/latency limits all require physical testing.
- Actual camera Color 2/4, P4/P5/P7 battery charging/recovery and saved recovery images remain untouched.

## Hardware acceptance required

Test with an inserted microSD on the physical Tab5: create session, add 25 laser-triggered events, finish, reboot, read files on laptop, intentionally remove card and test power interruptions. Confirm no corrupt old sessions, no false SAVED indicator, no shooting freeze and stable battery operation. Until this passes, do not call microSD recording complete.
